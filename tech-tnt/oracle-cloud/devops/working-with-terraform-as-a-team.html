Working with Terraform as a Team

Introduction​

That feeling of manually clicking through a web console to provision cloud resources is a familiar one. It's a time of uncertainty, where replicating an environment becomes a Herculean task and "it works on my machine" is a constant battle cry. Thankfully, Infrastructure as Code (IaC) tools like Terraform brought order to this chaos. Terraform allows you to define your desired infrastructure, from virtual machines to networks, in a declarative configuration file. It then provisions and manages those resources for you, turning your infrastructure from a manual process into a version-controlled, repeatable blueprint. But while a single engineer can use Terraform to manage their own environment, the real power is unlocked when a team of cloud and DevOps engineers collaborate, ensuring consistency and preventing the dreaded state drift.

For a team to effectively manage infrastructure with Terraform, a solid collaboration workflow is essential. Instead of each engineer working with a local copy of the configuration and state file, a shared approach is critical. By managing your Terraform configuration in a Git repository, every change is tracked, reviewed, and approved, just like with application code. This provides a clear audit trail and prevents accidental changes. The crucial final piece is securing the state file, which contains sensitive information about your infrastructure. Storing it in a shared, secure remote backend like the OCI Object Storage Service (OSS) prevents conflicts and enables state locking, ensuring that only one person can apply changes at a time. This collaborative process using Git and a remote backend is the foundation for building and managing robust, scalable, and reproducible OCI infrastructure as a team.

Manage Concurrency​

Terraform manages concurrency to prevent conflicts and state file corruption, which can occur when multiple users or automated processes attempt to apply changes simultaneously. This is achieved through a mechanism called state locking. When an operation like terraform apply is initiated, Terraform first attempts to acquire a lock on the state file. If a remote backend that supports state locking (such as OCI Object Storage, AWS S3 with DynamoDB, or Terraform Cloud) is configured, this lock is managed centrally. In the OSS bucket, you will see the file terraform.tfstate.lock when a someone has acquired a lock on the Terraform state.

While one user holds the lock, any other user or process attempting to run a state-modifying command will be blocked and will receive an error message indicating that the state is currently locked. Once the initial operation is complete, Terraform automatically releases the lock, allowing the next process to proceed. This serialized access to the state file ensures data integrity and prevents race conditions, making collaboration on shared infrastructure both safe and predictable.

Assumptions​

This Tech TnT guide assumes that the reader has some basic knowledge of the OCI and experience working with the following features and resources:

  • IAM
    • Create users.
    • Create groups.
    • Create policies and write policy statements.
    • Create API keys and gather the required information for connecting to the OCI REST APIs.
  • OSS
    • Create buckets.
  • Familiarity with using Git.

Task 1 - Set Up Prerequisite OCI Resources for Terraform Remote Backend​

Task 1.1 - Create IAM User and Group​

  1. Create an IAM group for cloud engineers to access the remote state files, for example, CloudEngineers.
  2. Create the cloud engineer's IAM user and assign them to the CloudEngineers group.

Task 1.2 - Create Object Storage Bucket​

Create an OSS bucket, e.g., tfstate-team. Activate the option to Enable Object Versioning. This helps preserves older versions of the state files, and protects against accidental deletions.

Task 1.3 - Create IAM Policy for User to Access Bucket​

To manage the state and lock files, the IAM user requires the following permissions:

  • OBJECT_INSPECT
  • OBJECT_CREATE
  • OBJECT_DELETE
  • OBJECT_READ

Create an IAM policy with the following statements:

Allow group 'Default'/'CloudEngineers' to read buckets in compartment cloudadmin
Allow group 'Default'/'CloudEngineers' to manage objects in compartment cloudadmin where all { target.bucket.name = 'tfstate-team' }

Modify the necessary values.

Task 2 - Create the New Terraform Project​

In the example Terraform project, the scripts will create a new compartment of the customer, and in it, a VCN with one public and two private subnets. Here are the current list of TF files:

FilenameDescription
backend.tfContains the backend configuration for storing the Terraform state.
compartment.tfA new compartment for isolating OCI resources for each customer.
data.tfStores the Terraform data sources used in the project.
providers.tfContains provider information.
terraform.tfDefines the required providers and versions for running the Terraform scripts.
variables.tfDeclares the variables used for deploying the OCI resources defined in this project.
vcn.tfDefines all the OCI resources for building the customer's VCN.

The user credentials used to provision the OCI resources are stored in the file provider.oci.auto.tfvars or provider.oci.auto.tfvars.json, and contains the following variables:

  • tenancy_ocid
  • user_ocid
  • fingerprint
  • private_key_path
  • private_key_password
  • region

Here's an example provider.oci.auto.tfvars.json:

{
    "tenancy_ocid": "ocid1.tenancy.oc1.***",
    "user_ocid": "ocid1.user.oc1..***",
    "fingerprint": "**:**:**:**:**:**:**:**:**:**:**:**:**:**:**:**",
    "private_key_path": "/path/to/privatekey.pem",
    "region": "us-phoenix-1",
    "private_key_password": null
}

A client-specific file is created to contain values for the following variables:

  • base_compartment_ocid
  • client_name
  • vcn_name
  • vcn_dns_label
  • vcn_cidr_block

For example, a configuration for Contoso (contoso.tfvars in the Git repository) might look like the following:

base_compartment_ocid = "ocid1.compartment.oc1..***"
client_name           = "contoso"
vcn_name              = "contoso"
vcn_dns_label         = "contoso"
vcn_cidr_block        = "10.100.0.0/16"

Backends​

The Terraform state files (named terraform.tfstate by default) are an essential component in the IaC ecosystem. It is a JSON-formatted file that serves as a single source of truth for your managed infrastructure. It is a persistent record of the resources Terraform has created and managed, acting as a map between your Terraform scripts and TFVARS files, and the OCI resources in your tenancy. The state file stores essential information such as resource OCIDs, attributes, and dependencies. Terraform uses this file to understand the current state of your infrastructure, which allows it to accurately plan and apply changes. By comparing the desired state in your configuration with the current state in the state file, Terraform can determine precisely what to create, update, or delete, ensuring that your infrastructure remains aligned with your code.

These are stored locally by default, but as mentioned in the introduction, this is not a good solution when operating as a team. Terraform introduced remote backends in version 0.11.13. It allows the management of the Terraform state files in remote systems such as AWS S3 buckets, Google Cloud Storage, and Postgres databases. OCI Object Storage is also one of the supported configurations, and you can find the documentation available here.

A basic configuration (see the file backend.tf in the example project) requires the bucket name and namespace. The region can be placed either in a .tfbackend files, an environment variable, or in the Terraform script. Here's an example:

terraform {
  backend "oci" {
    # Required
    bucket    = "tfstate-team"
    namespace = "***"
    region    = "us-phoenix-1"
  }
}

A set of user credentials is required to connect to the OSS. This is unique to each user, hence, the attributes listed should be stored separate from the backend.tf file, for example, a file named provider.oci.tfbackend. These are:

  • tenancy_ocid
  • user_ocid
  • fingerprint
  • private_key_path

IMPORTANT

Using the -backend-config results in Terraform storing the credential information locally in the local Terraform state file. If this is not desired (and it is recommended to) use OS environment variables with the same names, prefixed with OCI_.

Task 2 - Prepare the Project for Git​

If the project isn't already in Git, initialise it and set it to push to the desired repository.

git init

Add a suitable .gitignore file in the repository's root directory. You may use GitHub's template for Terraform or a tool like gitignore.io.

Along with the usual OS-specific ignores, I would add the following for Terraform:

.terraform/
*.tfstate
*.tfstate.*
crash.log
crash.*.log
override.tf
override.tf.json
*_override.tf
*_override.tf.json
.terraform.tfstate.lock.info
*tfplan*
.terraformrc
terraform.rc
*.dot
planout

# Added:
provider.*.auto.tfvars.json
provider.*.auto.tfvars
*.tfbackend
.secrets/

# Removed:
#*.tfvars
#*.tfvars.json

A few points of note:

  1. I have the pattern for provider.*.auto.tfvars.json and provider.*.auto.tfvars. I use files with this naming pattern to store my OCI credential information.
  2. The *.tfbackend is for storing the credentials needed to access the backend.
  3. The Terraform Style Guide and example .gitignore excludes TFVARS files because they could contain sensitive information. However, I feel that they contain variable values that defines the infrastructure. Hence, for sensitive variables, I would place them in a .secrets subdirectory, and reference them in the -var-file parameter when executing a plan, apply, or destroy action.

Finally, create the Git repository for the project with your favourite provider, then commit your work to the remote repository.

git remote add origin git@github.com:fuzziebrain/example-terraform-repository-for-teams.git
git branch -M main
git add .
git commit -m "Initial commit."
git push -u origin main

Task 3 - Perform Terraform Operations​

To begin working with the target tenant, first initialise the working directory, providing the OCI credentials for accessing the remote backend using the parameter -backend-config:

terraform init -backend-config="provider.oci.tfbackend"

While optional, consider using Terraform workspaces to compartmentalise each stack deployment. You can create a new workspace using the command:

terraform workspace new contoso

This creates a "directory" structure with the workspace prefix (default: tf-state-env) and the workspace name, e.g., contoso. You can list choose the desired workspace or show the current workspace using the commands terraform workspace select contoso and terraform workspace show respectively.

NOTE

While you can change the workspace prefix using the attribute workspace_key_prefix, I have ran into issues doing so when working with workspaces.

Next, run the plan command to get a preview of what changes are expected to be performed on the target tenant.

terraform plan -var-file=contoso.tfvars

Finally, after validating the expected outcomes, apply the changes:

terraform plan -var-file=contoso.tfvars

Voila!
