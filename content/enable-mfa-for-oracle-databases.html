Enable MFA for Oracle Databases

August 10, 2025 · 9 min read
Adrian Png
Director of Innovation, AI and Cloud Solutions @ Insum, a Talan Company

The recent Oracle Database 23ai 23.9 update included a new feature to further improve the security of Oracle Databases. Database owners can now opt to require users to authenticate with a multi-factor authentication (MFA) device. This can be performed either through push notifications on a compatible authenticator application or certificate-based authentication. The two currently supported authenticator applications are Cisco Duo or Oracle Mobile Authenticator (OMA). And according to this Oracle blog post, this cool security feature has been backported to 19c.

Required Ingredients​

Here are some essential components that will be required for this to work.

  1. Access to an Oracle Cloud Infrastructure (OCI) Identity Access Management (IAM) identity domain.
    1. The Domain URL
    2. An application registered, and its client ID and secret
  2. Access to the Oracle Database's file system and privileges to change the database's parameters.
  3. Access to an SMTP server. On the OCI, the Email Delivery services will work just fine and is used in the example below.
    1. SMTP host
    2. SMTP port
    3. SMTP username
    4. SMTP password
  4. If the OCI Email delivery service is used, an IAM user with capability to generate SMTP credentials, and permissions to send emails are required.

Prepare OCI​

To enable the MFA feature, there are some essential steps to be performed and information to be gathered in the OCI tenancy.

Identity Domain​

Domain URL​

An identity domain is required. Either use an existing domain or create a new one. Then go to the details page and obtain the Domain URL by clicking the Copy button next to it.

The port number 443 may be omitted.

Register an Integrated Application​

An OAuth client must be registered to this domain for the MFA feature to work.

  1. Navigate to the domain's Integrated applications page and add an application.
  2. Select Confidential Application, and click the button Launch workflow.
  3. Enter an appropriate name, and click the button Submit to create the application.
  4. Back on the application's details page, go to the OAuth configuration tab, then click the button Edit OAuth configuration.
  5. Under the Client configuration section, select the option Configure this application as a client now, and set the Allowed grant types to only Client credentials. Do not submit yet!
  6. Scroll down to the App roles section, and click the button Add app roles. Add the two required roles User Administrator and MFA Client, then click the button Submit.
  7. Back on the OAuth configuration tab, the Client ID and Client secret will now be available. Copy the values. For the secret, the button with the ellipsis has options to either Show or Copy the secret value.
  8. Finally, click on the dropdown menu Actions and activate the application.

Email Delivery Services​

If the OCI Email Delivery Services is used, then do the following:

  1. Create an IAM group, e.g., EmailDeliveryServicesUsers.
  2. Create an IAM policy with the following statement: 
    allow group 'Default'/'EmailDeliveryServicesUsers' to use email-family in compartment MyCompartment
  3. Create an IAM user and assign user to the group created in the earlier step. Optionally, restrict the user capabilities to allow it to generate SMTP credentials.
  4. Generate the SMTP credentials, and be sure to note down the SMTP username and password. The latter is displayed only once.
  5. Obtain the SMTP server information assigned to your region. This can be found in the service's configuration page. Note the Public Endpoint.
  6. IMPORTANT. The email address to be used when sending out OMA enrollment emails must be added to the service's list of Approved Senders. The sending domain's DNS must be configured to allow emails to originate from the OCI's SMTP servers.

Configure the Database​

Configure the database for MFA as the SYSDBA user. First, set the following parameters:

define domain_url = "https://idcs-***.identity.oraclecloud.com"
define region = "us-phoenix-1"
define email_from = "system@example.com"
define email_from_name = "System Email"

Then, execute the following parameter changes in the target PDB:

alter system set mfa_oma_iam_domain_url = "&domain_url.";
alter system set mfa_smtp_host = "smtp.email.&region..oci.oraclecloud.com";
alter system set mfa_smtp_port = 587;
alter system set mfa_sender_email_id = "&email_from.";
alter system set mfa_sender_email_displayname = "&email_from_name.";

Configure the Oracle Wallet​

An Oracle Wallet is used to store the OAuth client and SMTP credentials using the following aliases:

  • oracle.security.mfa.oma.clientid
  • oracle.security.mfa.oma.clientsecret
  • oracle.security.mfa.smtp.user
  • oracle.security.mfa.smtp.password

Before configuring the Oracle Wallet for MFA, query and obtain the PDB's container GUID (PDB_GUID), and the database's WALLET_ROOT.

select
  con_id_to_guid(con_id) as PDB_GUID
  , value as WALLET_ROOT
from v$parameter where upper(name) = 'WALLET_ROOT';

Login to the database server using SSH as the oracle user, set the environment variables, and create the wallet. You will need to provide a password, set in WALLET_PASSWORD, for the new Oracle Wallet.

WALLET_ROOT=/opt/oracle/dcs/commonstore/wallets/***
PDB_GUID=***
WALLET_PATH=$WALLET_ROOT/$PDB_GUID/mfa
read -s WALLET_PASSWORD

mkdir -p $WALLET_ROOT/$PDB_GUID
orapki wallet create -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -auto_login -compat_v12

The wallet will be created in the defined by WALLET_PATH, which in turn is define by $WALLET_ROOT/$PDB_GUID/mfa.

Next, set the required environment variables CLIENT_ID, CLIENT_SECRET, SMTP_USER, and SMTP_PASSWORD.

read CLIENT_ID
read -s CLIENT_SECRET
read SMTP_USER
read -s SMTP_PASSWORD

Execute the following orapki commands to set these values in the Oracle Wallet:

orapki secretstore create_entry -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -alias oracle.security.mfa.oma.clientid -secret $CLIENT_ID
orapki secretstore create_entry -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -alias oracle.security.mfa.oma.clientsecret -secret $CLIENT_SECRET
orapki secretstore create_entry -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -alias oracle.security.mfa.smtp.user -secret $SMTP_USER
orapki secretstore create_entry -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -alias oracle.security.mfa.smtp.password -secret $SMTP_PASSWORD

To inspect the set variables, you may run the following commands:

# List all entries.
orapki secretstore list_entries -wallet $WALLET_PATH -pwd $WALLET_PASSWORD

# View a specific entry using its alias.
orapki secretstore view_entry -wallet $WALLET_PATH -pwd $WALLET_PASSWORD -alias oracle.security.mfa.oma.clientid

Create or Update a User for MFA​

Now the easy part. Create a user and specify that in addition to their credentials, the user must authenticate with OMA.

create user demomfa identified by "&user_password."
  and factor 'OMA_PUSH' as '&user_email.';
grant connect,resource to demomfa;

Alternatively, an existing user can be enrolled using the ALTER USER command.

alter user demoold add factor 'OMA_PUSH' as '&user_email.';

If the associated email address (external name) needs to be changed, use the UPDATE FACTOR clause.

alter user demomfa update factor 'OMA_PUSH' as '&new_user_email.';

And finally, the MFA requirement can be removed with the DROP FACTOR clause.

alter user demoold drop factor 'OMA_PUSH';

You may check the MFA requirements and associated email address by querying the SYS.DBA_USERS view.

select username, mfa, external_name
from sys.dba_users
where username like 'DEMO%';

An observations about the email address or external names. If an external name is already associated with an existing user, then you can't use it to authenticate another user in the same database.

Error report -
ORA-28026: user with same external name already exists

https://docs.oracle.com/error-help/db/ora-28026/
28026. 0000 -  "user with same external name already exists"
*Cause:    The external name specified for the user being created or
        altered already exists for another user.
*Action:   External names must be unique among users.  Specify another.

More about this later.

Will this Work?​

In Oracle Database 19c​

YES, IT DOES!!! It was mentioned in the Alan William's blog post, mentioned in the released notes for 19.28, and I validated this to be true. However, there are some differences that you need to pay attention to, and make changes to the process described earlier in this article.

  1. The function CON_ID_TO_GUID doesn't exists in 19c. You can still set the PDB_GUID based on the following query: 
    select guid from v$pdbs;
  2. The secrets are stored in the Oracle Wallet using the mkstore command: 
    echo $WALLET_PASSWORD | mkstore -wrl $WALLET_PATH -createEntry oracle.security.mfa.oma.clientid $CLIENT_ID
    echo $WALLET_PASSWORD | mkstore -wrl $WALLET_PATH -createEntry oracle.security.mfa.oma.clientsecret $CLIENT_SECRET
    echo $WALLET_PASSWORD | mkstore -wrl $WALLET_PATH -createEntry oracle.security.mfa.smtp.user SMTP_USER
    echo $WALLET_PASSWORD | mkstore -wrl $WALLET_PATH -createEntry oracle.security.mfa.smtp.password $SMTP_PASSWORD

In an Oracle Autonomous Database​

This is a good question. For this to work, the credentials for the client and SMTP server is stored in an Oracle Database wallet placed within a specific directory defined by the WALLET_ROOT parameter. It also requires privileges to alter database parameters that we don't have. So short answer, I think not.

Error starting at line : 1 in command -

alter system set mfa_oma_iam_domain_url = "https://idcs-***.identity.oraclecloud.com"

Error report -

ORA-01031: insufficient privileges

https://docs.oracle.com/error-help/db/ora-01031/

01031. 00000 -  "insufficient privileges"

*Document: YES

*Cause:    A database operation was attempted without the required

           privilege(s).

*Action:   Ask your database administrator or security administrator to grant

           you the required privilege(s).

Closing​

I love this new feature, and the fact that Oracle decided to backport it to 19c.

As noted earlier, a user's email address can be associated with only one database account. Beyond securing Oracle Databases even further, I feel that enforcing MFA for database authentication provides even more reasons for database administrators to adopt the practice of:

  1. Disabling authentication for application schemas using the NO AUTHENTICATION clause.
  2. Provide individual user accounts and grant them either proxy access or necessary privileges to work with the application schemas.
